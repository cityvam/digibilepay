# اتصال دیتابیس واقعی (vamcityc_vamcity) به DigitalPay

## چه چیزی انجام شده
- بکاپ SQL Server 2019 (ویندوز) **بدون SQL Server** خوانده و استخراج شد؛ تعداد ردیف همه‌ی ۸۵ جدول کاربری دقیقاً با آمار خود SQL Server برابر است
  (مثلاً کاربران ۵۴٬۶۳۱، درخواست وام ۱۷٬۲۵۹، وام ۱٬۴۰۸، پرداخت ۲۹٬۲۴۴، تیکت ۵۴٬۱۹۷، اعتبارسنجی ۲٬۷۶۲).
- **پیش‌نمایش (web-next/mock/real-data.json)** با داده‌ی واقعی ساخته شد: ۱۱۲ طرح وام، شمارنده‌های داشبورد، نمونه‌ی ۴۰ تیکت/اعلام واریز/اعتبارسنجی/سفارش، نمایندگان.
  هویت‌ها ماسک شده‌اند: نام، شماره، کد ملی، هش رمز، متن تیکت و کلیدهای AppSettings **در این فایل نیستند**.
- برای سرور واقعی: `deploy-linux/restore-and-migrate.sh` بکاپ را روی SQL Server لینوکس Restore می‌کند، جدول‌های جدید را می‌سازد
  و `database/04-migrate-legacy-to-new-modules.sql` طرح‌های وام قدیمی (Loans) را به LoanProducts و برند را به Tenant منتقل می‌کند.

## اجرا روی لینوکس
```bash
export SA_PASSWORD='رمز-قوی'
mkdir -p backup && cp /path/to/vamcity.bak backup/vamcity.bak   # اگر داخل زیپ نیست
./deploy-linux/restore-and-migrate.sh
```
Connection string: `Server=localhost,1433;Database=vamcityc_vamcity;User Id=sa;Password=...;TrustServerCertificate=True`

## پیش‌نمایش محلی
`cd web-next && npm i && npm run mock` (یا `node tools/demo/build-demo.mjs` برای ساخت دموی یک‌فایلی).
بازتولید real-data.json از بکاپ: `BAK=backup/vamcity.bak tools/bak-reader/run.sh` (فقط پایتون ۳).

## محدودیت‌ها و فرض‌ها (صادقانه)
- اسکریپت 04 و restore-and-migrate.sh روی SQL Server واقعی **اجرا نشده‌اند**؛ اول روی کپی دیتابیس تست کنید.
- **واحد پول دیتابیس تومان است** (با داشبورد قدیمی تطبیق داده شد: جمع وام‌ها ۱۸۱٬۶۱۹٬۱۸۱٬۰۹۳، با بهره ۲۳۲٬۰۲۰٬۵۷۵٬۳۹۰، وصول‌شده ۲۵٬۰۱۸٬۸۹۳٬۷۱۴). تیکت وضعیت ۰ = در انتظار بررسی (۱ مورد، مطابق داشبورد قدیمی).
- بقیه‌ی کدهای وضعیت از روی تعداد حدس زده شد و باید با enum های C# قدیمی تطبیق داده شود:
  تیکت 0=باز، 2=بسته، 3=پاسخ‌داده‌شده؛ اعتبارسنجی 4=انجام‌شده، 1=در صف، 2و3=ناموفق؛ اعلام واریز 1=تأییدشده؛ روش پرداخت 2=کارت‌به‌کارت، 4=آنلاین.
- DelayPercent/EarlyPercent در 04 به‌صورت «درصد روزانه ÷ ۱۰۰» به LateDailyCoef/EarlyDailyCoef رفته؛ با ContractEngine تطبیق دهید.
- حداقل مبلغ طرح در جدول قدیمی نیست (۰ گذاشته شد)؛ AllowedInstallments قدیمی داخل ConditionsJson ذخیره می‌شود نه TiersJson.
- بخش‌هایی از پنل که به جدول‌های قدیمی (کاربران، وام‌ها، اقساط) وابسته‌اند هنوز به API واقعی وصل نیستند؛ کنترلرهای C# آن‌ها در بسته نبود.
- فایل .bak و dump شامل اطلاعات شخصی و کلیدهای واقعی (درگاه، پیامک) است؛ آن را در گیت یا جای عمومی نگذارید.

## دیتابیس دوم: vamcityc_transferDb (درگاه انتقال وجه)
- بکاپ دوم (`backup/transferdb.bak`، ۴ مگابایت) هم مستقیم خوانده شد: ۱۴ جدول، از جمله `Transfer` (۲۳ انتقال از ۱۴۰۲/۱۰ تا ۱۴۰۲/۱۲، ۶ موفق، جمع ۱۱٬۸۰۱٬۰۰۰ تومان)، `Client` (کلاینت `vamcity.com`) و ورود (Identity) مخصوص خودش. ساختار `Transfer` همان `OnlineMoneyTransfer` دیتابیس اصلی است (Id، Amount، From، To، OTP، TransferStep، EFardaJson).
- مبلغ بر حسب **تومان** است (پاسخ بانک: مبلغ ۱۰٬۰۰۰ برای ۱٬۰۰۰ تومان).
- صفحه‌ی جدید **/admin/transfers** (منوی «مالی و اعتبار») هر دو منبع را نشان می‌دهد: ۲۷۱ انتقال دیتابیس اصلی (۷۳ موفق، جمع ۲٫۸۶ میلیارد تومان؛ ۱۸۱ ناموفق، ۱۷ در انتظار کد تأیید) و آمار درگاه قدیمی. کنترلر C# آن `backend/enterprise/files/TransfersController.cs` است؛ برای آمار درگاه، رشته‌ی اتصال `ConnectionStrings:TransferDb` را بگذارید.
- ارتباط دو دیتابیس فقط برای ۳ ردیف (`OurTraceNumber` ↔ `ClientTraceNumber`) پیدا شد؛ درگاه قدیمی (EFarda) تا ۱۴۰۲/۱۲ بوده و انتقال‌های بعدی با ارائه‌دهنده‌ی «شاهین» مستقیم در دیتابیس اصلی ثبت شده‌اند.
- امنیت: کد OTP، رمز/هش کلاینت و توکن‌ها هرگز در API یا پیش‌نمایش نمی‌آیند؛ حساب/شبا ماسک می‌شوند. فایل‌های `.bak` را جای عمومی نگذارید.
